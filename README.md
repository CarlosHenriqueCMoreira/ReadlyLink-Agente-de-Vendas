# Readly Link — Sales Diagnosis with PostgreSQL and dbt

Data engineering project that answers a business question:
**what is stopping the customer from buying, and what should be done about each lost customer?**

A Python ETL loads the history of 1,000 simulated readers and 2,400 simulated
service interactions into PostgreSQL. dbt models the data, explains each
abandonment with the cause that shows up in the data, compares the old
recommendation logic with new business rules, and generates an action for
each lost interaction. A visual page shows the answers to the client's 23
questions.

> Synthetic data generated for demonstration purposes.

## Key results

| Question | Answer |
|---|---|
| How many service interactions end without a purchase? | 1,468 of 2,400 (61.2%) |
| Main causes | Recommendation mismatch (461), price above budget (451), couldn't find the next book in the series (295) |
| Recommendations that comply with all rules | 37.9% before → 93.9% after |
| Gifts matching the recipient's genre | 9.6% before → 94.3% after |
| Cases with an automatic solution | 1,262 of 1,468 (86.0%) |
| Cases requiring human review | 206 (14.0%) |

All answers, with the calculated figures, are in
[`docs/respostas_perguntas.md`](docs/respostas_perguntas.md). The file is
generated by the pipeline itself (`scripts/escrever_respostas.py`).

## Architecture

    data/*.csv
       │  Python ETL (extract → transform → load)
       ▼
    PostgreSQL · raw schema            (data as received, everything as text)
       │  dbt
       ▼
    staging        types, cleanup, digital's 9999 → unlimited_stock
    intermediate   book history, reader profile, service context,
                    rules engine (int_candidatos_atendimento)
    marts           dimensions and facts, evidenced reasons, funnel, before/after,
                    new recommendation, per-interaction solution
       │  scripts/exportar_metricas.py  (queries the marts → JSON)
       │  scripts/escrever_respostas.py (JSON → text for the 23 answers)
       ▼
    business_metrics.json + docs/respostas_perguntas.md → visual page

Details in [`docs/arquitetura.md`](docs/arquitetura.md).

## The rules engine

A book is **suitable** for a service interaction when:

1. it is available in the requested format (digital is always available);
2. it fits the declared budget;
3. the customer hasn't read it yet (for gifts, the buyer's history doesn't count);
4. it respects the series order: volume 1, or the previous volume was already read;
5. it matches the requested genre.

If the customer asked for the book by name, or it is the next volume in their
series, rules 4 and 5 don't apply.

The score ranges from 0 to 100: requested book 30, genre 30, tone 15, format
15, and up to 10 for budget headroom. Each recommendation comes with a
justification sentence generated from the customer's data.

## Quality

- **121 dbt tests**: uniqueness, nulls, relationships, accepted values, and
  business-logic tests. Among them:
  - `motivo_abandono_coerente` and `motivos_tem_evidencia`: no abandonment reason without evidence in the data;
  - `solucao_respeita_regras`: no solution above budget, already read, or out of series order;
  - `recomendacao_respeita_regras`: the new recommendation never violates the rules;
  - `pontuacao_diferencia_livros`: the score must vary to explain the choices;
  - `estoque_digital_sem_numero_ficticio`: the source's 9999 placeholder never reaches the marts.
- **10 pytest tests**: extraction, transformation, and data generator consistency.

## How to run it

Commands are run from the project root.

### 1. Python environment

    python3 -m venv .venv
    source .venv/bin/activate
    python -m pip install -r requirements.txt

### 2. Environment variables

    cp .env.example .env

Then adjust the password in `.env`.

### 3. PostgreSQL

    docker compose up -d
    docker compose ps

### 4. (Optional) Regenerate the simulated data

    python scripts/gerar_dados_negocio.py

### 5. ETL

    python src/main.py

Expected output:

    ETL concluído: 1000 usuários carregados em raw.usuarios_csv.
    Dados de negócio carregados: 96 em raw.catalogo_livros, 2400 em raw.atendimentos, 932 em raw.vendas.

### 6. dbt models and tests

    set -a; source .env; set +a
    dbt build --project-dir readly_dbt --profiles-dir readly_dbt

### 7. Visual page, answers, and dbt documentation

    ./scripts/gerar_documentacao.sh
    dbt docs serve --project-dir readly_dbt --profiles-dir readly_dbt

The page opens at `index.html`. dbt's technical documentation is at `dbt-docs.html`.

### 8. Python tests

    pytest -q

### Ready-made queries

`sql/consultas_analiticas.sql` has one query per block of questions.
For example: evidenced reasons, before/after, per-interaction action, and
recommendation with the score broken down.

### Dropping the local database

This command removes the PostgreSQL volume and all its data:

    docker compose down -v

## What was fixed in this version

| Problem in the previous version | Fix |
|---|---|
| 228 of 303 "price" abandonments actually had a price **within** budget | The generator now only records a reason when the cause actually exists. Two tests enforce this |
| The same title had two IDs (physical and digital), so "already read" failed on the other format | `livro_id` now identifies the work (series + volume). The original ID lives in `edicao_id` |
| The "out of stock" solution offered the same product that had already been recommended | The interaction now records `livro_procurado_id`. The solution offers that book in another format or a similar one |
| Solutions offered books already read, above budget, or out of series order | Single rules engine, with the `solucao_respeita_regras` test |
| All 1,000 customers scored 100, and the example came out in alphabetical order | The score is split by criterion, and the justification is generated per customer |
| Digital stock showed as "9,999 in stock" | `estoque_ilimitado` (unlimited stock). The page shows "Digital · always available" |
| Gifts used the buyer's own reading history | New question: "for whom?" For gifts, the buyer's history is no longer used |
| Page numbers were hardcoded in the HTML | All numbers and answers now come from the JSON generated from the marts |
| No before/after comparison | `mart_antes_depois` compares both recommendations on the same interactions |
